# ГимРум

Мессенджер для общения внутри **МБОУ Кировская Гимназия**. Личные диалоги и
групповые чаты, сообщения приходят мгновенно, работает в браузере — и на
компьютере, и на телефоне (iPhone и Android), откуда его можно поставить на
домашний экран как обычное приложение.

## Что умеет

**Переписка**
- Личные диалоги один-на-один и групповые чаты
- Мгновенная доставка без перезагрузки страницы
- Ответы с цитированием и правка своих сообщений: у изменённого на виду время
  правки, а убранное исчезает целиком — без строчки «сообщение удалено», вокруг
  которой потом идёт весь разговор
- Реакции эмодзи
- Вложения: картинки (показываются прямо в ленте), документы, PDF
- Картинка открывается поверх переписки — с увеличением щипком и колесом, без
  ухода в отдельную вкладку
- Перед отправкой картинку можно поправить: обрезать, замазать лишнее
  («мозаикой», из которой фамилию уже не прочитать) и обвести карандашом
- Поиск по всем своим перепискам и по людям
- Меню чата: профиль или участники, уведомления, выбор нескольких сообщений,
  очистка переписки у себя, блокировка, выход из группы
- У группы может быть своя картинка — ставит её создатель
- Диалог, в котором ещё ничего не написали, в списке чатов не задерживается:
  человек остаётся в недавних, откуда его убирают крестиком

**Мелочи, из которых складывается ощущение живого мессенджера**
- Кто сейчас в сети и «был(а) 5 минут назад»
- «Печатает…»
- Счётчики непрочитанного и черта «Непрочитанные» в ленте
- Галочки «отправлено / прочитано»
- Уведомления о новых сообщениях: в браузере, на телефоне и в приложении
- Тёмная и светлая темы
- Раскладка под телефон, можно поставить на домашний экран как приложение
- Группы «без звука»

**Группы по коду**
- У каждой группы свой код из шести символов, например `CFH6QK`
- Создатель передаёт код — остальные входят сами, без приглашений вручную
- Код можно сменить: старый сразу перестаёт работать
- В кодах не используются похожие друг на друга символы: `O` и `0`, `I`, `1`, `L`.
  Код диктуют вслух и переписывают от руки, и путаница здесь дороже пары
  лишних комбинаций

**На телефоне**
- Раскладка под один экран: список чатов или переписка
- Учитывается вырез сверху и полоса жеста снизу
- Поле ввода не уезжает под клавиатуру
- Страница не приближается сама при касании поля
- Действия над сообщением открываются касанием, а не «залипают» после него
- Вернулись в приложение — новые сообщения появляются сразу, не дожидаясь
  переподключения

**Люди и поиск**
- Поиск по имени («Иванов») и по логину («ivanov» или «@ivanov»), варианты
  показываются по мере набора
- Точное совпадение логина стоит первым, дальше — начало имени, потом
  совпадения в середине
- Нажатие на найденного человека или на имя в чате открывает карточку: аватар,
  логин, класс или должность, «о себе», был ли в сети. Переписка начинается
  кнопкой «Написать» из этой карточки
- Логин можно менять в профиле: раз в неделю, а прежний два месяца остаётся
  закреплён за вами

**Вход и устройства**
- Вход запоминается: заходить каждый день заново не нужно, а пока человек
  пользуется мессенджером, срок сам отодвигается
- Флажок «Чужой компьютер» на входе: сессия живёт до закрытия браузера и не
  продлевается — следующий за этим компьютером не попадёт в чужую переписку
- В профиле видно, где ещё открыт аккаунт, и есть кнопка «Выйти на других
  устройствах» на случай забытого входа в компьютерном классе
- Смена пароля и блокировка закрывают все сессии сразу, включая открытые
  вкладки

**Управление**
- Регистрация: логин, пароль и класс. Отображаемое имя можно задать потом
  в профиле — до этого показывается логин
- Классы гимназии: с 1 по 11, литеры О, Г и Э. Класс обязателен: регистрируются
  ученики, а аккаунты учителям заводит администратор
- Свободная регистрация (по умолчанию) или закрытый режим по кодам-приглашениям
- Создатель группы переименовывает её, добавляет и убирает участников
- Первый зарегистрировавшийся становится администратором

**Администрирование**
- Панель открывается щитом в шапке боковой панели — она видна только
  администратору
- Список всех аккаунтов с поиском по имени и логину
- Аккаунты учителям заводятся вручную: имя, логин, пароль. Класс у них не
  указывается, рядом с именем стоит «Учитель»
- Блокировка аккаунта с причиной: вход закрывается, открытые вкладки перестают
  работать сразу, причину человек видит при попытке войти
- Новый пароль вместо забытого — без старого пароля; все устройства этого
  человека выходят из аккаунта
- Свой аккаунт и аккаунты других администраторов через панель не меняются

## Быстрый старт

Нужен Node.js 20+ и любая база PostgreSQL.

```bash
npm install
cp .env.example .env.local     # укажите DATABASE_URL и AUTH_SECRET
npm run db:push                # создать таблицы
npm run dev                    # http://localhost:3000
```

Секрет для кук удобно сгенерировать так:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Хотите сразу посмотреть на заполненный интерфейс, не регистрируя всех вручную:

```bash
npm run db:seed   # 5 демо-аккаунтов, пароль у всех: gimroom-demo
                  # заодно печатает код демо-группы для проверки входа по коду
```

## Развёртывание на Vercel + Neon

1. **Заведите базу.** В [Neon](https://console.neon.tech) создайте проект и
   скопируйте строку подключения — ту, где в адресе есть `-pooler`.
   Подойдёт и Vercel Postgres, и Supabase, и свой сервер: код обычный
   PostgreSQL, ничего специфичного для Neon в нём нет.

2. **Создайте таблицы.** С той же строкой подключения выполните локально:

   ```bash
   DATABASE_URL="postgresql://…" npm run db:push
   ```

3. **Залейте проект на Vercel** (импорт репозитория с GitHub) и пропишите
   переменные окружения.

   Важно про порядок: переменные подхватывает только новая сборка. Если
   добавить их к уже собранному проекту, приложение продолжит отвечать
   «Не задан адрес базы данных», пока не будет сделан Redeploy — или пока
   не придёт следующий коммит в ветку, из которой собирается production.

   Переменные:

   | Переменная | Зачем |
   |---|---|
   | `DATABASE_URL` | Строка подключения к базе (обязательно) |
   | `AUTH_SECRET` | Случайная строка от 32 символов для подписи сессий (обязательно) |
   | `INVITE_ONLY` | `true` — регистрация только по коду. По умолчанию открытая |
   | `ADMIN_USERNAME` | Кому выдать права администратора при регистрации |
   | `REGISTRATION_LIMIT` | Сколько регистраций в час с одного адреса (по умолчанию 60) |

   Названия гимназии, список классов и длина кодов заданы в `src/lib/config.ts` —
   если что-то из этого изменится, править нужно только там.

4. Откройте адрес и зарегистрируйтесь первым — этот аккаунт получит права
   администратора.

Никакой отдельной настройки Vercel не требуется: приложение обходится обычными
маршрутами Next.js и не нуждается в WebSocket-сервере (см. ниже).

## Как это устроено

Обычное приложение на Next.js (App Router) и PostgreSQL. Внешних сервисов нет,
из зависимостей — только Next, React и драйвер `pg`.

```
src/lib/         работа с базой, сессии, проверка ввода, лента событий
src/app/api/     маршруты API
src/components/  интерфейс
db/schema.sql    схема базы
scripts/         применение схемы и демо-данные
tests/           модульные и сквозные проверки
```

Решения, которые стоит пояснить.

**Мгновенная доставка без WebSocket.** На serverless-хостинге вроде Vercel негде
держать постоянный сокет и общую шину между экземплярами функции. Поэтому
источник правды — таблица `events` в базе: любое изменение пишет туда строку, а
клиенты читают её по курсору через Server-Sent Events. Экземпляры ничего не
знают друг о друге, при обрыве связи ничего не теряется (браузер сам присылает
`Last-Event-ID`), и ровно тот же код работает на своём сервере. Задержка — доли
секунды: пока идёт разговор, лента опрашивается часто, в тишине реже.

**Файлы лежат в базе.** У serverless нет постоянного диска, а заводить отдельное
хранилище ради школьного чата — лишняя деталь, которую придётся настраивать и
оплачивать. Файлы хранятся в Postgres с ограничением 8 МБ на файл. Если объёмы
вырастут, менять придётся только `src/app/api/files/`.

**Место ограничено, и кончается оно сразу у всех.** Бесплатная база — это
полгигабайта на всё, вместе с перепиской. Если её забить фотографиями, встанет
не только загрузка файлов: кончившееся место останавливает любую запись, то есть
и обычные сообщения. Поэтому пределов три (`config.storage`): 100 МБ на человека
за всё время, 30 МБ в сутки — чтобы место нельзя было занять за один вечер, — и
350 МБ на всю гимназию, после которых загрузка закрывается для всех. Каждый видит
свою полоску в профиле, а отказ приходит до записи файла и объясняет, в какой
именно предел упёрлись. Картинки вдобавок ужимаются ещё в браузере: сторона до
1600 точек и тот формат из двух, что вышел легче.

**Пароли и сессии.** Пароли хешируются `scrypt` со случайной солью. В куке лежит
случайный токен, в базе — только его HMAC, так что утечка таблицы сессий не даёт
готовых кук. Кука `httpOnly`, `sameSite=lax`, в продакшене `secure`.

**Высота экрана на телефоне.** Единицы `dvh` учитывают исчезающую адресную
строку, но не клавиатуру: на iOS при её появлении разметка остаётся прежней, и
строка ввода уезжает вниз. Настоящую видимую высоту знает только
`visualViewport` — приложение слушает его и держит свою высоту по нему
(`src/lib/useViewport.ts`).

**Пороги защиты от перебора** считаются на аккаунт, а не только на адрес: школа
выходит в сеть через один IP, и класс, регистрирующийся на одном уроке, не
должен блокировать сам себя.

**Две разные роли под одним словом.** В базе `users.role` — кто человек в
гимназии (`member`, `teacher`, `admin`), а `conversation_members.role` — кто он
в конкретной группе (`owner`, `member`). Наружу вторая уходит как `role`,
первая — как признак `isTeacher`, чтобы их нельзя было перепутать.

**Уведомления показывает service worker, а не страница.** На Android
конструктор `new Notification` запрещён вовсе — Chrome требует
`ServiceWorkerRegistration.showNotification`, и раньше уведомлений на телефонах
не было совсем: вызов молча падал в `catch`. Нажатие приходит в `sw.js`, а не на
страницу, поэтому оттуда окно поднимается и получает сообщение с номером чата;
если мессенджер был закрыт, чат передаётся в адресе (`/?chat=…`).

Своё окно на Windows — третий случай: WebView2 веб-уведомления не показывает
вовсе, их должна показать программа-хозяин. Страница узнаёт его по метке
`window.__gimroomNative` и вместо уведомления отправляет сообщение наружу, а
приложение мигает значком в панели задач.

**Вход запоминается, но не везде одинаково.** Обычный вход — кука на месяц,
которая продлевается при заходе (`renewSession`, не чаще раза в сутки, чтобы не
писать в базу на каждый запрос). «Чужой компьютер» — кука вообще без срока
жизни: браузер удалит её при закрытии, а сама сессия живёт восемь часов и не
продлевается. Одна галочка на входе, а разница принципиальная: в компьютерном
классе за тем же местом через урок сидит другой человек.

**Освободившийся логин не отдаётся сразу.** Логин можно менять, и без резерва
вышло бы так: человек сменил «ivanov» на «ivanov_i», а через минуту «ivanov»
занял кто-то другой — и пишет от его имени тем, кто помнит старый логин.
Поэтому прежний логин уходит в таблицу `released_usernames` и два месяца
достаётся только своему хозяину (`config.usernameChange`). Там же пауза между
сменами: логин — это то, по чему человека ищут, и мелькать он не должен.

**Блокировка обрывает сессии.** Заблокировать — значит удалить строки из
`sessions`, а не только пометить аккаунт: иначе открытая вкладка доработала бы
до конца срока куки. Проверка `blocked_at IS NULL` стоит и в чтении сессии
(`src/lib/auth.ts`) — на случай, если блокировка случится в ту же секунду, что и
запрос. Права администратора панель не выдаёт: их получает первый
зарегистрировавшийся или тот, кто указан в `ADMIN_USERNAME`.

## Тесты

Модульные проверки чистых функций — запускаются сразу:

```bash
npm test
```

Сквозные проверки API ходят по настоящему HTTP, поэтому им нужны отдельная база
и запущенный сервер:

```bash
createdb gimroom_test
DATABASE_URL="postgresql://localhost/gimroom_test" npm run db:push
DATABASE_URL="postgresql://localhost/gimroom_test" AUTH_SECRET="test-secret-0123456789abcdef" \
  npx next start -p 3100 &
BASE_URL=http://127.0.0.1:3100 npm run test:api
```

База должна быть пустой: набор проверяет админ-панель, а права администратора
достаются первому зарегистрировавшемуся. Перед повторным прогоном пересоздайте
базу (`dropdb gimroom_test && createdb gimroom_test && npm run db:push`).

Они проверяют в том числе то, что легко сломать незаметно: посторонний не
читает чужую переписку и не скачивает чужие вложения, удалённое сообщение не
уезжает клиенту вместе с текстом, загруженный HTML отдаётся как обычный текст и
не может выполниться на нашем домене.

Отдельный раздел «Безопасность» повторяет атаки из аудита — попытки поднять
себе права, подделать сессию, подставить мусор вместо идентификатора, перебрать
пароль — и проверяет заголовки защиты. Он нужен, чтобы эти защиты нельзя было
потерять незаметно при будущих правках.

Раздел «Админ-панель» проверяет, что в неё не попадает ни ученик, ни гость, что
заблокированный не входит даже с верным паролем и теряет открытую сессию, что
новый пароль закрывает старые устройства и что администратора нельзя завести
через панель.

## Безопасность

Приложение проверено настоящими атаками по HTTP — то есть ровно тем, что можно
сделать из консоли браузера по F12. Ниже — что проверено и что осталось за
рамками.

### Клиент ничему не верит

Всё, что приходит от браузера, — предположение, а не факт. В консоли F12 можно
послать любой запрос, минуя интерфейс: поменять чужой идентификатор, дописать
себе роль администратора, отправить сообщение от чужого имени. Поэтому права
проверяются на сервере при каждом запросе, а не в интерфейсе.

Проверено атаками (`tests/api.test.mjs`, раздел «Безопасность»):

| Попытка | Что происходит |
|---|---|
| Дописать `role: "admin"` в регистрацию или в профиль | Роль назначает сервер, поле из запроса игнорируется |
| Подменить себе логин через профиль | Логин менять нельзя |
| Открыть чужую переписку по её номеру | 404 — даже факт существования диалога не подтверждается |
| Написать в чужой диалог, отредактировать или удалить чужое сообщение | 404 / 403 |
| Отправить сообщение от чужого имени (`senderId` в запросе) | Отправителем становится владелец сессии |
| Скачать чужое вложение по его номеру | 404; гостю — 401 |
| Подсмотреть чужие сообщения в ленте событий | Лента отдаёт только диалоги, где человек состоит |
| Подделать токен сессии | 401 |
| Подставить `1 OR 1=1` вместо номера | 400 — разбор строгий, `parseInt` молча вернул бы 1 |
| `'; DROP TABLE users; --` в поиск | Запросы параметризованы, текст остаётся текстом |

### Пароли

Хешируются `scrypt` (N=32768, r=8, p=1, ключ 64 байта) со случайной солью в
16 байт на каждого. Сравнение — постоянного времени, чтобы по нему нельзя было
подбирать посимвольно.

Одна проверка стоит около 90 мс и 32 МБ памяти. Это специально: перебор
миллиона вариантов занял бы порядка суток на ядро, а требование памяти делает
малополезными видеокарты, на которых обычно и перебирают. Восемнадцать
аккаунтов с одинаковым паролем дают восемнадцать разных хешей — соль работает.

Сам пароль нигде не хранится, не логируется и не возвращается в ответах.

**Перебор ограничен на двух уровнях:** 10 попыток входа за 15 минут на
конкретный аккаунт и 5 попыток подтвердить текущий пароль при его смене. Второе
важнее, чем кажется: добравшись до незапертого ноутбука, пароль можно
подбирать, чтобы сменить его и увести аккаунт насовсем.

**Существование аккаунта не выдаётся.** Ответ одинаков для неверного пароля и
несуществующего логина — и по тексту, и по времени. Изначально проверка пароля
для несуществующего логина пропускалась, ответ приходил в 20 раз быстрее, и по
одному этому можно было перебрать список зарегистрированных в гимназии. Теперь
работа выполняется одинаковая в обоих случаях.

### Сессии

В куке лежит случайный токен на 256 бит, в базе — только HMAC от него: утечка
таблицы сессий не даёт готовых кук. Кука `HttpOnly` (скрипт со страницы её не
прочитает), `SameSite=Lax` (не уходит на чужие сайты — защита от CSRF), в
продакшене `Secure`. После выхода кука перестаёт действовать сразу, а смена
пароля гасит сессии на всех остальных устройствах.

### Защита от внедрения чужого кода

React вставляет пользовательский текст как текст, а не как разметку, и ссылки в
сообщениях собираются узлами React — сообщение физически не может стать
HTML. Поверх этого работает Content-Security-Policy как последний рубеж:

- Скрипты разрешены только по одноразовому ключу (`nonce`), своему на каждый
  ответ. Ни `unsafe-inline`, ни `unsafe-eval` в рабочей сборке нет.
- Обработчик в атрибуте (`<img onerror=…>`) — классический XSS — браузер
  выполнять отказывается. Проверено.
- Скрипт с чужого домена не загрузится.
- `frame-ancestors 'none'` и `X-Frame-Options: DENY` — страницу нельзя открыть
  в чужом фрейме и подменить нажатия.
- `nosniff`, `Referrer-Policy`, отключённые камера, микрофон и геолокация.

Загруженные файлы отдаются отдельно и строже: текст и HTML — как `text/plain`
вложением, SVG — только скачиванием (это XML, из него исполняется скрипт), у
всех — запрещающий всё CSP и `nosniff`. Иначе загруженная страница выполнилась
бы на нашем домене и добралась до чужих сессий.

### Шифрование переписки — что есть и чего нет

**По дороге** трафик шифруется TLS: Vercel выдаёт HTTPS сам, а `Secure` на куке
и `upgrade-insecure-requests` в политике не дают приложению работать по
открытому HTTP. Одноклассник в той же школьной сети переписку не перехватит.

**В базе** сообщения лежат открытым текстом. Диск у Neon шифруется, но это
защита от кражи диска, а не от того, у кого есть доступ к базе:
администратор гимназии, хостинг и любой, кто добудет `DATABASE_URL`, прочитают
переписку.

**Сквозного шифрования (E2E) нет.** Это осознанный выбор, а не упущение:

- Поиск по сообщениям и уведомления работают на сервере — с E2E сервер видит
  только шифротекст, и то и другое пришлось бы переносить на устройство.
- Ключи живут на устройствах. Забыл пароль, сменил телефон, почистил браузер —
  переписка потеряна навсегда, восстановить её некому.
- Групповые чаты с приходящими и уходящими участниками требуют протокола вроде
  MLS с ротацией ключей. Это отдельный проект, а не настройка.

Практический вывод: **обещать детям тайну переписки не нужно.** «ГимРум»
защищён от одноклассника с открытой консолью — но не от того, у кого есть
доступ к базе. Так устроено большинство школьных и рабочих чатов; важно, чтобы
это было сказано прямо.

### Открытые вопросы

- **Регистрация свободная.** Зарегистрироваться может любой, кто узнает адрес.
  Чтобы закрыть круг, поставьте `INVITE_ONLY=true` — тогда нужен код из таблицы
  `invites`:

  ```sql
  INSERT INTO invites (code, max_uses) VALUES ('SHKOLA-2026', 30);
  ```

- **Первый зарегистрировавшийся становится администратором.** Зарегистрируйтесь
  сразу после развёртывания, до того как адрес разойдётся.

- **Код группы — это ключ от неё.** Любой, кто узнал код, войдёт, пока код не
  сменили. Для класса это удобно; для чего-то закрытого лучше добавлять людей
  вручную и сменить код после набора.

- **Администратор может удалять чужие сообщения**, но не читать чужие личные
  диалоги через интерфейс.

- **Уведомления по электронной почте не предусмотрены**, поэтому и
  восстановления пароля по почте нет: забытый пароль сбрасывает администратор
  прямо в базе.
